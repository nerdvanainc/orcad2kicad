# orcad2kicad 사용자 설명서

제공: Nerdvana Inc. (㈜너드바나) — https://www.nerdvana.co.kr · 다운로드/문서: https://github.com/nerdvanainc/orcad2kicad

OrCAD Capture로 그린 회로도를 KiCad 프로젝트(`.kicad_sym`/`.kicad_sch`/`.kicad_pro`,
필요하면 `.kicad_pcb`까지)로 변환하는 도구다. 입력은 OrCAD `.DSN` 파일 자체(권장, OrCAD
설치 불필요, 0장), OrCAD Capture가 뽑은 EDIF 2.0.0 익스포트(대안 경로, 1~13장), 또는 이미
KiCad로 임포트해 둔 프로젝트 중 하나를 고른다. 이 문서는 이 도구를 처음 보는 엔지니어가
설치부터 KiCad에서 결과를 확인하기까지 혼자 따라갈 수 있도록 쓴 것이다. 이 문서는 "사용법"에
집중한다 — 배포 패키지에는 이 문서와 `Quick_Start.md`, `README.md`, `LICENSE`,
`THIRD_PARTY_NOTICES.md`가 함께 들어 있다.

## Quick Start (핵심만)

OrCAD `.DSN` 하나를 정식 KiCad 10.0 프로젝트로 바꾸고 검증까지 끝내는 최단 경로다. 자세한 설명은
각 장으로.

**1. 준비 (한 번만)**
- 정식 KiCad 10.0 이 설치돼 있으면 된다(편집·검증은 전부 정식판으로 한다).
- `dist\orcad2kicad.exe` 를 실행한다(설치 없음). 소스라면 `python -m orcad2kicad`.
- 입력 프레임의 **[나이틀리 KiCad 포터블 준비(설치 없음)]** 를 한 번 누른다 — `.DSN` 을 읽는
  임포터가 아직 나이틀리에만 있어서다. 내려받아 압축만 풀며(약 300 MB) 설치 프로그램은 실행하지
  않는다. 이후로는 자동 탐지된다.

**2. 입력 파일 3개 (같은 폴더에 두면 자동으로 채워진다)**
| 파일 | 필수 | 어디서 | 용도 |
|---|---|---|---|
| `이름.DSN` | 필수 | OrCAD 프로젝트 | 회로도 원본 |
| `이름.asc` (PADS2000 넷리스트) | 권장 | OrCAD Create Netlist → PADS | 검증 정답([3]). 없으면 연결 검증을 못 한다 |
| 배선된 PADS Layout ASCII `.asc` | 권장 | PADS Layout File → Export ASCII(전체 섹션) | 풋프린트 라이브러리(`PADS.pretty`)·보드 연결·[4] 대조 |

**3. GUI 실행**
1. 입력 종류에서 **OrCAD .DSN** 을 고르고 `.DSN` 파일을 찾는다. 출력 폴더(`<이름>_kicad`),
   프로젝트 이름, 같은 폴더의 넷리스트/보드가 비어 있던 칸에 자동으로 들어간다.
2. **[변환 실행]**. 상태가 `완료 (모든 검증 PASS)` 이면 끝. `검증 FAIL 있음` 이면 검증 탭의 넷 표를 본다.
3. **결과 탭의 "요약 설명"** 을 읽는다 — 각 검증이 무엇을 확인했는지, ERC 항목이 조치가 필요한지,
   결론이 한 번에 적혀 있다.
4. **[KiCad 프로젝트 열기]** 로 정식 KiCad 10.0 에서 연다. 회로도는 루트 시트 + 페이지별 하위 시트
   구조다.

CLI 로 같은 일:
```
orcad2kicad-cli.exe --dsn 이름.DSN --netlist 이름.asc --board 보드.asc --explain
```
(출력 폴더는 `.DSN` 옆 `이름_kicad`, `-o` 로 바꿀 수 있다.)

**4. 결과 읽는 법 (요약)**
- `[3] … RESULT: PASS` — KiCad 회로도의 연결이 OrCAD 넷리스트와 100% 같다. 이것이 핵심 판정.
- `[4] refs only on board: []`, `BOARD NETS: PASS` — 보드와 회로도의 부품·넷이 같다. 차이가 있으면
  "보드 차이" 탭에서 항목별로 처리한다(보드에만 있는 부품은 회로도에 자리표시 추가/무시 등).
- ERC 수백 건은 대부분 임포터 특성·KiCad 관례 차이(격자 이탈, 미접속 표시 없음, PWR_FLAG 없음)로
  연결과 무관하다. 요약 설명이 유형별로 "정보/확인 권장/조치 필요"를 표시한다.

**5. KiCad 에서 마무리**
- Pcbnew 에서 **Update PCB from Schematic(F8)** 을 실행해 보드와 회로도를 연결한다. 풋프린트는
  `PADS:<데칼>` 로 보드 라이브러리(`PADS.pretty`)와 이어져 있어 부품이 다시 놓이지 않는다.
- 이후 회로도 수정 → F8 반복. 나이틀리는 더 이상 필요 없다.

## 0. OrCAD 없이 변환하기 (권장 경로)

2026-07경 KiCad 코드베이스에 **OrCAD `.DSN` 네이티브 임포터**가 병합됐다(`kicad-cli sch import
--format orcad`, `kicad-cli import`로 `.DSN`+PADS 보드를 한 프로젝트로). 이 덕분에 **OrCAD
Capture 자체가 없어도** `.DSN` 파일 하나로 변환을 시작할 수 있다 — OrCAD를 곧 지울 계획이라면
이 경로가 1~13장의 "EDIF 익스포트" 경로보다 앞선 권장 경로다. EDIF 경로(1~13장)는 여전히 그대로
지원되며, OrCAD가 설치돼 있고 KiCad 8~10 정식판만 쓰는 경우에는 지금처럼 EDIF를 쓰면 된다.

### 왜 "나이틀리"가 필요한가

이 임포터는 **아직 정식 릴리스에 없다** — 병합된 것은 개발 브랜치(나이틀리, 버전 `10.99.x`)뿐이고,
정식 반영은 **KiCad 11부터**로 예상된다(이 문서 작성 시점 KiCad 10.0.6이 최신 정식판). 그래서
`--dsn`(OrCAD `.DSN` 자체를 읽는 것)에는 **나이틀리 `kicad-cli`**가 반드시 있어야 한다.

**하지만 그 뒤 결과는 정식 KiCad 10.0 포맷으로 저장된다.** 나이틀리 임포터가 만드는 결과(최상위
시트 여러 개, 포맷 `20260830` 등 정식판이 못 여는 형태)는 이 도구가 자동으로 루트 시트 + 하위
시트 구조(포맷 `20260306`)로 재구성한다(기본 동작, `--nightly-format`으로 끌 수 있음) — 그래서
**편집·[3] 검증·ERC·PDF는 정식 KiCad 10.0/kicad-cli만으로 전부 된다.** 보드(`.asc`) 임포트도
정식 kicad-cli가 있으면 그쪽을 쓴다(정식판이 못 여는 `.kicad_pcb` 버전이 나오지 않도록). 즉
나이틀리가 필요한 것은 **`.DSN`을 처음 읽는 그 순간뿐**이고, `--kicad-project`(이미 KiCad
프로젝트로 임포트해 둔 것을 입력으로 쓰는 경우)는 애초에 나이틀리가 전혀 필요 없을 수도 있다
(입력이 이미 정식 포맷이면 재구성도 건너뛴다).

### 나이틀리 준비 — 자동(권장) / 수동 / 정식 설치

> **이 도구는 설치 프로그램을 실행하지 않는다.** 나이틀리 설치본(NSIS 자체 압축 실행 파일)을
> 내려받아 **압축만 푼다**. 레지스트리·시작 메뉴·파일 연결에 아무것도 남지 않고, 이미 쓰고
> 있는 정식 KiCad 10과 섞이지 않는다.
>
> **압축 도구(7-Zip/Bandizip)가 없는 PC여도 된다.** 그런 PC에서는 7-Zip 콘솔판을 공식
> 사이트에서 받아 **역시 압축만 풀어서** 쓴다(약 6 MB, `<설치위치>\tools\7zip\`).
> 7-Zip 설치 프로그램도 실행하지 않는다.

**1) 자동(권장) — 버튼/플래그 하나로 끝난다**

- GUI: "입력" 프레임의 **[나이틀리 KiCad 포터블 준비(설치 없음)]** 버튼. 확인 창에서 계속을
  누르면 최신 나이틀리를 받아 압축을 풀고, 끝나면 위의 "kicad-cli 경로" 칸이 자동으로 채워지고
  설정에 저장된다. 진행 상황은 "로그" 탭에 그대로 나온다.
- CLI:
  ```bash
  PYTHONPATH=src python -m orcad2kicad.cli --fetch-kicad-nightly
  ```
  출력 마지막 줄이 `portable kicad-cli: <경로> (10.99.0, orcad import: yes)`. 다른 위치에
  두려면 `--fetch-kicad-nightly D:\kicad-nightly` 처럼 폴더를 붙인다.
- 이미 받아 둔 설치본이 있으면(사내망 등 네트워크가 막힌 PC) 다운로드를 건너뛴다:
  ```bash
  PYTHONPATH=src python -m orcad2kicad.cli --fetch-kicad-nightly \
    --kicad-nightly-installer D:\down\kicad-nightly-10.99.0.3703.gaa01e4fd3b-x86_64-lite.exe
  ```
- MCP 서버를 쓰는 경우: 툴 `prepare_kicad_nightly`(인자 `root`/`installer`/`force`, 전부 선택).

무슨 일이 일어나는지:

| 단계 | 내용 |
|---|---|
| 목록 | https://downloads.kicad.org/kicad/windows/explore/nightlies 를 읽어 **최신 x86_64 lite** 빌드를 고른다(빌드 번호가 가장 큰 것) |
| 다운로드 | 설치본 `.exe` 약 **234 MB** 를 `<설치위치>\.cache\` 로 받는다(`.part` 로 받은 뒤 이름을 바꾸므로 중간에 끊긴 파일이 남지 않는다) |
| 압축 도구 | 시스템의 정식 7-Zip(`7z.exe`)이나 Bandizip을 쓴다. 없으면 **자급**: `7zr.exe`(약 590 KB, 퍼블릭 도메인) → 그것으로 7-Zip x64 배포본(약 1.6 MB)을 풀어 정식 `7z.exe`(약 5.9 MB) 확보. 전부 다운로드+압축 해제뿐 |
| 압축 해제 | 위 도구로 나이틀리 설치본을 **푼다**(설치기는 실행하지 않는다) |
| 정리 | `share\kicad\demos`(약 350 MB), `share\kicad\internat`(약 49 MB), `$PLUGINSDIR`, `uninstall.exe` 삭제 → **725 MB → 약 326 MB**(실측) |
| 확인 | `kicad-cli version` 과 `sch import --help` 를 실제로 실행해 버전과 OrCAD 임포트 지원을 확인하고 `portable.json` 에 기록 |

- **설치 위치(기본)**: `%LOCALAPPDATA%\orcad2kicad\kicad-nightly`
  (보통 `C:\Users\<사용자>\AppData\Local\orcad2kicad\kicad-nightly`).
  그 안에 `bin\kicad-cli.exe`, 기록 파일 `portable.json`, 받은 설치본 `.cache\*.exe` 가 있다.
- **디스크**: 정리 후 약 **330 MB**(+ 캐시에 남긴 설치본 234 MB — 지워도 된다.
  압축 도구를 자급했다면 `tools\` 약 8 MB가 더해지는데, 그중 6 MB는 다음에도 쓰는 7-Zip이다).
- **소요 시간**: 압축 해제 약 **6초**(NVMe 실측). 대부분은 다운로드 시간이다.
- **두 번째부터는 즉시 끝난다** — 이미 준비돼 있으면 네트워크에 접속하지 않고 경로만 돌려준다.
- **최신으로 갱신**: `--fetch-kicad-nightly --force-fetch` (GUI에서는 아래 "삭제" 후 버튼을 다시
  누른다). 옛 `bin`/`lib`/`share`/`etc` 를 지우고 새로 푼다.
- **삭제**: 위 폴더를 통째로 지우면 끝이다(설치한 것이 아니므로 제거 프로그램이 없다).
- **압축 도구는 없어도 된다.** 시스템에 정식 7-Zip(`7z.exe`)이나 Bandizip(`bz.exe`)이 있으면
  그것을 쓰고(PATH 또는 `C:\Program Files\7-Zip\7z.exe`, `C:\Program Files\Bandizip\bz.exe`
  자동 탐지, `O2K_EXTRACTOR`로 강제 지정 가능), **없으면 7-Zip 콘솔판을 스스로 마련한다**:

  1. `https://www.7-zip.org/a/7zr.exe` (약 590 KB, 퍼블릭 도메인)를 받는다.
     이 단독판은 NSIS를 열지 못하지만, 7-Zip 자신의 배포용 `.exe`는 풀 수 있다.
  2. `https://www.7-zip.org/a/7zNNNN-x64.exe` (약 1.6 MB)를 받아 `7zr x`로 푼다 →
     정식 `7z.exe`(+`7z.dll`, `License.txt`, 약 5.9 MB)가 `<설치위치>\tools\7zip\`에 생긴다.
     **7-Zip 설치 프로그램으로 실행하지 않는다.**
  3. 그 `7z.exe`로 KiCad 나이틀리 설치본을 푼다.

  마련한 7-Zip은 다음 실행에서 그대로 재사용된다. 출처·크기·라이선스 고지는
  `<설치위치>\tools\7zip\SOURCE.txt`와 그 옆의 `License.txt`(LGPL, unRAR 제한 포함)에 있다.
  자급이 싫으면 `--no-download-tools`(CLI) 또는 MCP 인자 `download_tools: false` — 그 경우
  압축 도구가 없으면 "7-Zip/Bandizip을 설치하거나 아래 2)처럼 수동으로 푸시오"라고 안내하며
  실패한다. **어느 경우에도 설치 프로그램을 실행하라고 하지 않는다.** Windows 전용이다.
- **`7za.exe`/`7zr.exe` 단독판은 NSIS를 열지 못한다**(오류 없이 "Files: 0"만 나온다). 그래서
  PATH에 그것들만 있어도 시스템 압축 도구로 인정하지 않고 위 자급 절차를 탄다.

**2) 수동(압축 도구는 있지만 도구를 안 거치고 싶을 때)**

같은 `.exe`를 받아 **설치하지 않고** Bandizip 또는 7-Zip으로 그냥 압축 풀듯이 풀면 그 안에
`bin\kicad-cli.exe`가 나온다. 예:
```
"C:\Program Files\Bandizip\bz.exe" x kicad-nightly-10.99.0.xxxxxxx-x86_64-lite.exe -o:C:\kicad-nightly
7z x -y -oC:\kicad-nightly kicad-nightly-10.99.0.xxxxxxx-x86_64-lite.exe
```
결과: `C:\kicad-nightly\bin\kicad-cli.exe`. (Bandizip은 정상적으로 다 풀고도 종료 코드 2를
내는 일이 있다 — `bin\kicad-cli.exe`가 생겼으면 성공이다. 이 도구도 같은 기준으로 판정한다.)

**3) 정식 설치(원한다면)**

https://downloads.kicad.org/kicad/windows/explore/nightlies 에서 `kicad-nightly-*.exe`를 받아
평소처럼 설치해도 된다. 정식 KiCad와 별도 폴더에 나란히 설치되므로 기존 KiCad 10을 지울 필요는
없다. 다만 시스템에 흔적이 남으므로, 1)이나 2)를 권한다.

**경로 알려주기** — 어느 방법이든:
   - CLI: `--kicad-cli "C:\kicad-nightly\bin\kicad-cli.exe"` (직접 지정, 최우선)
   - 환경변수 `O2K_KICAD_NIGHTLY`에 실행 파일 경로를 지정(자동 탐지 후보에 추가됨, `--kicad-cli`를
     안 줘도 됨) — 정식 설치했다면 `%ProgramFiles%\KiCad Nightly*\bin\kicad-cli.exe` 등도
     자동으로 찾는다(탐지 순서는 직접 지정 → 환경변수 → PATH → OS별 표준 설치 경로 → 위에서
     준비한 포터블 나이틀리 폴더).
   - GUI: "입력" 프레임의 "kicad-cli 경로" 칸에 직접 지정하거나 비워 두면 자동 탐지 결과가
     채워진다. 옆의 회색 안내문 "나이틀리(10.99+)는 .DSN 임포트에만 필요. 결과는 정식 KiCad
     10.0 포맷으로 저장됨"이 언제 나이틀리가 필요한지 알려준다.
   - 위 1)로 준비한 것은 **아무것도 지정하지 않아도** 자동 탐지된다
     (`%LOCALAPPDATA%\orcad2kicad\kicad-nightly\bin\kicad-cli.exe` 가 나이틀리 후보에 포함된다).

### CLI 예시

```bash
PYTHONPATH=src python -m orcad2kicad.cli --dsn MYBOARD.DSN \
  --board MYBOARD_board.asc \
  --netlist MYBOARD.asc \
  -o out/dsn --project MYBOARD --pdf --issues
```
PowerShell:
```powershell
$env:PYTHONPATH = 'src'
python -m orcad2kicad.cli --dsn MYBOARD.DSN `
  --board MYBOARD_board.asc `
  --netlist MYBOARD.asc `
  -o out/dsn --project MYBOARD --pdf --issues
```

이미 KiCad(나이틀리든 직접 임포트한 것이든)로 `.DSN`을 프로젝트로 바꿔 둔 상태라면 `--dsn`
대신 `--kicad-project`로 그 `.kicad_pro`를 바로 넣을 수 있다(재임포트 없이 우리 도구의 보드
연동·검증만 적용):

```bash
PYTHONPATH=src python -m orcad2kicad.cli --kicad-project C:\work\MYBOARD\MYBOARD.kicad_pro \
  --board MYBOARD_board.asc \
  --netlist MYBOARD.asc -o out/kp --issues
```

두 모드 모두 EDIF가 없으므로 리포트 첫머리에 `input mode: dsn`(또는 `kicad-project`)과
`[1]/[2] skipped: no EDIF`가 찍힌다 — [1] EDIF 조인, [2] 지오메트리 검증은 EDIF가 있어야만
가능하기 때문이다(7장 참고). [3] kicad-cli 넷리스트 검증과 [4] 보드 대조는 EDIF 경로와 동일하게
그대로 수행된다.

### GUI 사용

"입력" 프레임 맨 위 라디오 **"입력 종류: EDIF / OrCAD .DSN (KiCad 나이틀리 필요) /
KiCad 프로젝트(.kicad_pro)"**에서 원하는 쪽을 고르면 그에 맞는 파일 입력칸만 활성화된다(나머지
두 칸은 비활성화). 이후 넷리스트/보드/출력 폴더 등 나머지 항목은 EDIF 경로와 완전히 동일하게
채우고 "변환 실행"을 누르면 된다. 검증 탭에는 [1][2]가 없다는 안내(`[1][2] EDIF 없음 — 건너뜀`)가
맨 위에 뜬다.

### 풋프린트 필드 채우기: 보드 -> 넷리스트(.asc) -> 빈 값 (3단계-B, `fp-fallback`)

`--kicad-project`/`--dsn` 입력 모드에서 각 레퍼런스의 Footprint 필드는 아래 우선순위로 채워진다
(EDIF 입력 경로는 원래부터 OrCAD Footprint 값이 있으므로 이 폴백은 그 값이 **비어 있을 때만**
같은 순서로 적용된다):

1. **보드 데칼이 있으면 그것을 쓴다** — `PADS:<데칼>` (`--board`로 읽은 `.kicad_pcb`/`.asc` 기준,
   기존 동작).
2. **보드에 없고 `--netlist`가 있으면** OrCAD가 내보낸 PADS2000 `.asc`의 `*PART*` 섹션
   (`REF  FOOTPRINT` 한 줄씩)에서 그 레퍼런스의 풋프린트 이름을 찾는다.
   - 그 이름이 (대소문자 무시) 보드의 어떤 데칼과 같으면 그 데칼로 통일한다(`PADS:<데칼>`) —
     예: 넷리스트 이름 `so8`와 보드 데칼 `SO8`은 같은 것으로 본다.
   - `--board`가 있는데 같은 데칼이 없으면(예: 넷리스트 `SO8` vs 보드에 있는 건 `SO8NB`처럼
     이름이 다른 경우) **라이브러리 접두사 없이 넷리스트 이름 그대로** 채우고 레퍼런스별로
     이슈를 남긴다: `"{REF}: footprint {이름} from netlist has no PADS library entry"` — PADS
     라이브러리에 이 이름의 데칼이 없으니 KiCad에서 직접 확인/지정하라는 뜻.
   - **`--board` 없이 `--netlist`만 줘도** 이 단계만으로 채워진다(보드 연동 없는 넷리스트 단독
     실행 지원) — 이때는 비교할 보드 데칼 자체가 없으므로 레퍼런스마다 이슈를 남기지 않고(전부
     "라이브러리에 없음"이라 뻔하고 반복적이라서) 요약 한 줄만 남긴다:
     `"footprints filled from netlist only (no board): N refs; names are bare OrCAD footprint
     names without a library"`.
3. **그마저 없으면**(보드에도 없고 넷리스트에도 그 레퍼런스가 없거나 이름이 비어 있음) 필드를
   빈 채로 두고 이슈를 남긴다: `"{REF}: no footprint source (not on board, not in netlist)"`.

정상적인 PADS 라이브러리라면 안 생기는 경우지만, 방어적으로 **보드 데칼 두 개가 대소문자만
다르면**(예: `SO8`와 `so8`) 사전순으로 앞선 쪽(대문자가 소문자보다 앞선다 — `SO8`)을
결정적으로 골라 쓰고 이슈를 한 줄만 남긴다: `"board decals differ only by case: SO8, so8
(keeping SO8)"`.

리포트에는 `footprint fields: A set from board, B from netlist, C empty` 한 줄로 세 출처의
개수가 찍힌다. 어떤 레퍼런스가 어느 출처로 채워졌는지는 `PipelineResult.footprint_sources`
(`{ref: 'board'|'netlist'|''}`, MCP/GUI용 JSON `result_to_json()`의 `footprint_sources` 키에도
그대로 담김)로 확인할 수 있다.

EDIF 입력 경로(`kicad_writer.write_project`)는 보드에 없는 레퍼런스의 OrCAD Footprint 값이
**비어 있을 때만** 위 2번과 같은 방식으로 넷리스트 이름을 채운다(이슈:
`"{REF}: not on board; footprint from netlist: {이름}"`). OrCAD 값이 이미 있으면(대부분의 경우)
기존 동작 그대로 그 값을 유지한다.

### 제한 (`--dsn`/`--kicad-project` 전용)

- **보드 전용 부품 자동 추가(자리표시 심볼) 미지원.** EDIF 경로의 "보드 차이" 탭
  "회로도에 추가"/`--add-board-part`는 이 두 모드에서는 이슈 한 줄만 남기고 무시된다(임포트된
  회로도에 새 페이지를 쓰는 것은 후속 과제) — J19/J20류 보드 전용 부품은 [4] 리포트에서
  정보로만 확인하고, 회로도 반영은 KiCad에서 직접 하거나 EDIF 경로를 쓸 것.
- **`--footprint-choice`/`--pin-type`도 이 두 모드에서는 미지원**(풋프린트는 항상 보드
  기준, 핀 타입은 임포트된 심볼 그대로) — 이슈 한 줄만 남고 진행된다.
- **(기본 동작으로 해결됨) KiCad 10 정식판에서 `--dsn`/`--kicad-project` 결과 파일이 열리지
  않던 문제.** 나이틀리 임포터 결과(최상위 시트 여러 개, 포맷 예 `20260830`)를 이 도구가
  자동으로 루트 시트 + 하위 시트 구조(포맷 `20260306`, 정식 10.0.6 의 상한)로 재구성하므로,
  **기본값 그대로 실행하면** 결과가 정식 KiCad 10.0 으로 바로 열리고 편집된다(3단계-C-2).
  `--nightly-format` 을 준 경우에만 예전처럼 나이틀리 원본 포맷을 유지하며, 그때는 아래가
  그대로 해당한다: 나이틀리로만 열고 편집할 수 있고 **설치는 필요 없다**([나이틀리 KiCad
  포터블 준비]로 풀어 둔 폴더의 `bin\kicad.exe` 가 완전한 KiCad GUI, 설정은 정식판과 별도
  폴더 `%APPDATA%\kicad\10.99` 에 저장되어 서로 간섭하지 않는다). GUI 의 결과 탭
  [KiCad 프로젝트 열기] 버튼은 포맷을 보고 자동으로 이 포터블 kicad.exe 를 쓰고, CLI 는
  로그에 `note: schematic format … open with: …` 로 경로를 알려 준다.
- **나이틀리는 매일 바뀐다.** 버전(`10.99.x`)·회로도 포맷 버전·명령행 옵션이 예고 없이
  바뀔 수 있다 — 이 문서와 코드의 `SCH_FORMAT_CEILING`/`supports_orcad_import` 판별은 특정
  나이틀리 빌드(`10.99.0.3703`, 2026-09-09 기준) 실측이며, 다른 빌드에서는 재확인이 필요할 수
  있다. 재현이 안 되면 나이틀리를 최신으로 다시 받아 볼 것.

### OrCAD 삭제 전 체크리스트

OrCAD를 지우기 전에 최소한 아래를 해 둘 것을 권장한다(다시 필요해질 때 되돌릴 방법이 없어진다):

1. **`.DSN`과 `.OLB`(라이브러리) 파일을 반드시 보관한다** — 이 도구와 KiCad 나이틀리 임포터
   모두 `.DSN`만 있으면 되지만, `.OLB`가 없으면 OrCAD에서 다시 열어 확인할 방법이 없어진다.
2. **(권장, 안전망) 지금 EDIF 2.0.0과 PADS `.asc` 넷리스트도 한 번 뽑아 둔다**(4.2·4.3절
   절차) — `.DSN` 임포트 결과를 검증할 정답 기준이 되고, 나이틀리 임포터에 예상치 못한 문제가
   생겨도 기존 EDIF 경로로 되돌아갈 수 있다.
3. 여러 프로젝트가 있다면 1·2번을 프로젝트마다 반복한다(OrCAD Capture Tcl 스크립트로
   EDIF/넷리스트 일괄 익스포트를 자동화하는 방안은 검토만 됐고 아직 구현되지 않았다).

## 1. 개요

- **입력 종류(셋 중 하나를 고른다)**:
  1. **OrCAD `.DSN`**(권장 경로, 0장) — OrCAD Capture 없이 `.DSN` 파일 하나로 시작한다.
     `.DSN`을 읽는 것 자체는 KiCad 나이틀리(10.99+, 포터블로 설치 없이 준비 가능)의
     네이티브 임포터가 하지만, 그 뒤 편집·검증·ERC·PDF는 전부 정식 KiCad 10.0으로 한다.
  2. **EDIF 2.0.0**(대안 경로, 1~13장 전체) — OrCAD Capture에서 익스포트한 회로도. OrCAD가
     설치돼 있고 KiCad 정식판만 쓰는 경우 이 경로를 그대로 쓰면 된다. 결정적 리더가 직접
     파싱하므로 EDIF 조인([1])과 지오메트리([2]) 검증까지 함께 할 수 있는 유일한 경로다.
  3. **KiCad 프로젝트(`.kicad_pro`)** — `.DSN`을 KiCad(나이틀리든 다른 방법이든)로 이미
     임포트해 둔 것을 재임포트 없이 그대로 입력으로 쓴다.

  세 경로 모두 추가로 OrCAD가 뽑은 PADS2000 형식 넷리스트(`.asc`, 선택 — 넷 연결이 맞는지
  자동 대조하는 기준)와 PADS Layout ASCII 보드 파일(`.asc` 또는 이미 임포트된 `.kicad_pcb`,
  선택 — 풋프린트 매핑과 보드/회로도 대조에 사용)을 함께 줄 수 있다.
- **출력**: KiCad 프로젝트(`.kicad_pro`/`.kicad_sch`/`.kicad_sym`), 선택 시
  `.kicad_pcb`(PADS 보드 임포트 결과 + 풋프린트 라이브러리), PDF, ERC 결과, kicad-cli가
  뽑은 넷리스트. `.DSN`/KiCad 프로젝트 입력의 회로도는 기본적으로 정식 KiCad 10.0이 여는
  루트 시트 + 하위 시트 구조로 재구성해 저장한다(자세한 내용은 0장·10장).
- **핵심 원칙**: 변환·검증은 **전부 결정적**이다. 같은 입력이면 항상 같은 출력이 나오고,
  API 키나 인터넷 연결 없이도 전체 기능이 동작한다. AI(에이전트)는 선택 사항이며
  **제안만** 한다 — 무엇을 적용할지는 항상 사람이 GUI 표에서 고른다.
- **세 가지 실행 방법**: tkinter GUI(`python -m orcad2kicad`, 엔지니어가 파일을 고르고
  버튼을 눌러 쓰는 방식), CLI(`python -m orcad2kicad.cli ...`, 스크립트/자동화용),
  MCP 서버(`python -m orcad2kicad.mcp_server`, Claude Code 같은 외부 AI 도구가 접속해
  변환·검증을 직접 실행하는 방식). 셋 다 내부적으로 같은 `pipeline.run_pipeline()`
  함수 하나를 호출하므로 결과가 항상 동일하다.

## 2. 요구사항

| 항목 | 내용 |
|---|---|
| OS | Windows(개발·테스트 환경). tkinter/표준 라이브러리만 쓰므로 이론상 다른 OS에서도 동작하지만 검증되지 않았다. 포터블 나이틀리 자동 준비(`--fetch-kicad-nightly`)는 Windows 전용이다. |
| Python(소스로 실행할 때) | 3.10 이상. 런타임 의존성은 표준 라이브러리뿐(anthropic SDK 등 추가 설치 불필요 — `agents.py`는 API를 표준 라이브러리 `urllib`로 직접 호출한다). |
| **정식 KiCad(설치, 필수에 가까움)** | **10.0 계열 권장**(`kicad-cli` + GUI가 함께 설치돼 있어야 함). 어느 입력 경로든 편집·ERC·[3] 넷리스트 검증·PDF 출력·(`.asc`) 보드 임포트는 이 정식판 하나로 다 된다. 8 이상이면 대체로 동작하지만 이 문서의 실측값은 전부 KiCad 10.0.6 기준. kicad-cli가 아예 없어도 EDIF 읽기 + 1·2차 검증 + `.kicad_sym`/`.kicad_sch` 출력까지는 그대로 동작한다(EDIF 경로 한정 — `.DSN`/KiCad 프로젝트 경로는 임포트·회로도 읽기 자체에 kicad-cli가 필요하다). |
| **포터블 KiCad 나이틀리(설치 아님, `.DSN` 경로에서만 필요)** | `.DSN` 파일 자체를 읽는 것은 아직 나이틀리(10.99+)에만 있는 기능이라, **`--dsn`/`.DSN` 입력을 쓸 때만** 필요하다. GUI 버튼 하나(또는 `--fetch-kicad-nightly`)로 설치 없이 압축만 풀어 준비하며, 정식 KiCad와 별도 폴더에 있어 서로 간섭하지 않는다(0장). `.EDF`나 이미 임포트된 `.kicad_pro`만 쓴다면 이 나이틀리는 전혀 필요 없다. |
| exe로 실행할 때 | 위 요구사항 중 KiCad(정식판 kicad-cli, `.DSN`을 쓸 경우 나이틀리)만 그대로 필요하다. Python은 exe 안에 들어 있어 별도 설치가 필요 없다. |
| AI 에이전트(선택) | 아무것도 설치하지 않아도 된다(백엔드 `없음`이 기본). 쓰려면 8장 참고. |

## 3. 설치

### 3.1 exe로 설치 (일반 사용자에게 권장)

1. GitHub 릴리스 페이지(https://github.com/nerdvanainc/orcad2kicad/releases)에서 최신
   `orcad2kicad-<버전>-win64.zip`을 내려받는다. 안에는 `orcad2kicad.exe`(GUI),
   `orcad2kicad-cli.exe`(CLI/MCP), 이 문서를 포함한 문서 파일들이 들어 있다.
   같은 페이지의 `SHA256SUMS.txt`로 다운로드한 zip의 SHA-256 해시를 대조해 무결성을
   확인할 수 있다(`certutil -hashfile orcad2kicad-<버전>-win64.zip SHA256` 등으로 비교).
2. zip을 원하는 폴더에 압축 해제한다(설치 프로그램이 아니므로 레지스트리 등록·시작 메뉴
   등록이 없다 — 폴더를 옮기거나 지우면 그만이다).
3. `orcad2kicad.exe`를 더블클릭하면 GUI가 뜬다.
4. Windows SmartScreen/백신이 처음 실행 시 경고를 낼 수 있다 — 11장 "문제 해결" 참고.
5. 빌드를 직접 하려면(개발자) 아래 "소스 + 빌드" 항목과 `packaging/build_exe.cmd`를 참고.

### 3.2 소스에서 실행 (개발자, 또는 Linux·macOS 사용자)

> 소스는 GitHub(https://github.com/nerdvanainc/orcad2kicad)에 MIT 라이선스로 공개되어 있다. exe는 Windows용이고,
> 표준 라이브러리만 쓰는 순수 Python이라 Linux·macOS에서는 소스로 바로 실행할 수 있다(kicad-cli 경로만 자동 탐지 또는 지정).

```bash
git clone https://github.com/nerdvanainc/orcad2kicad.git
cd orcad2kicad
python -m pip install --upgrade pip     # 표준 라이브러리만 쓰므로 추가 설치는 원래 필요 없다
```

PowerShell:
```powershell
$env:PYTHONPATH = 'src'
python -m orcad2kicad          # GUI
python -m orcad2kicad.cli -h   # CLI 도움말
```

bash(Git Bash 포함):
```bash
PYTHONPATH=src python -m orcad2kicad
PYTHONPATH=src python -m orcad2kicad.cli -h
```

### 3.3 소스에서 exe로 빌드 (개발자)

```
packaging\build_exe.cmd            REM GUI(orcad2kicad.exe) + CLI/MCP(orcad2kicad-cli.exe) 둘 다 빌드
packaging\build_exe.cmd --cli-only REM CLI/MCP exe만 빌드(tkinter 없이 더 빠름)
```

- PyInstaller가 설치돼 있어야 한다(`python -m pip install pyinstaller`).
- 저장소 루트에서 실행해야 한다(`REPO_ROOT`를 스크립트가 자동으로 상위 폴더로 잡는다).
- 결과물은 `dist\orcad2kicad.exe`, `dist\orcad2kicad-cli.exe` (작업 파일은
  `build\pyinstaller\`, 둘 다 gitignore 대상).
- kicad-cli는 빌드에 포함되지 않는다 — exe도 실행 시점에 시스템에 설치된 kicad-cli를
  자동 탐지한다(PATH → 환경변수 `KICAD_CLI` → OS별 표준 설치 경로).

## 4. 입력 파일 준비

세 입력 경로(0장) 중 하나를 준비하면 된다. **4.1의 `.DSN` 경로가 권장이다** — OrCAD Capture가
필요 없다. OrCAD Capture로 EDIF를 계속 뽑을 수 있는 환경이면 4.2의 EDIF 경로도 그대로 쓸 수
있다(둘 다 검증·출력 방식은 동일하고, EDIF 경로만 [1][2] 검증이 추가로 붙는다). 4.3(넷리스트)·
4.4(보드)는 두 경로 모두에 공통으로 적용된다.

### 4.1 OrCAD `.DSN` (권장 경로) — OrCAD Capture 불필요

1. 변환할 프로젝트의 `.DSN` 파일 하나만 있으면 된다(OrCAD Capture로 새로 뽑을 필요 없이,
   기존에 갖고 있던 프로젝트 폴더의 `.DSN`을 그대로 쓴다).
2. `.DSN`을 실제로 읽는 것은 KiCad 나이틀리(10.99+)의 네이티브 임포터다 — 아직 이 기능이
   정식 릴리스에 없기 때문이다. 준비는 **[나이틀리 KiCad 포터블 준비(설치 없음)]** 버튼
   (또는 `--fetch-kicad-nightly`) 한 번이면 끝난다. 자세한 이유·과정은 0장 참고.
3. 임포트 결과는 기본적으로 정식 KiCad 10.0이 여는 포맷으로 재구성되므로, 그 뒤 확인·수정은
   전부 정식 KiCad 10.0으로 한다 — 나이틀리는 `.DSN`을 읽는 그 순간에만 관여한다.
4. GUI/CLI에는 `.DSN` 파일 경로 하나만 지정하면 된다(GUI의 "OrCAD .DSN 파일" 칸, CLI의
   `--dsn FILE`).

### 4.2 EDIF 2.0.0 (대안 경로) — OrCAD Capture 필요

OrCAD Capture가 설치돼 있고, KiCad 정식판만으로 계속 작업할 계획이면 이 경로를 그대로 써도
된다. EDIF 리더가 회로도를 직접 파싱하므로 [1] EDIF 조인·[2] 지오메트리 검증(7장)까지
`.DSN` 경로보다 한 단계 더 깊이 확인할 수 있다는 장점이 있다.

1. OrCAD Capture 17.x에서 변환할 프로젝트(.dsn)를 연다.
2. `File → Export Design...`
3. 익스포트 형식으로 **EDIF 2.0.0**을 선택한다(다른 EDIF 버전은 파서가 검증하지 않았다).
4. 결과로 `.EDF`(대문자/소문자 확장자 둘 다 인식) 파일 하나가 나온다. 이 파일이
   `--edf`/GUI의 "EDIF 파일" 입력이다.

### 4.3 PADS2000 넷리스트 (선택, 강력 권장) — 검증용 정답

1. OrCAD Capture(또는 OrCAD Layout 연동 메뉴)에서 `Tools → Create Netlist...`
2. 넷리스트 형식으로 **PADS**(PADS2000 계열, `.asc`)를 선택해 생성한다.
3. 이 파일을 `--netlist`/GUI의 "PADS 넷리스트(.asc)"에 지정하면, 변환 결과의 넷 연결이
   이 파일과 REF.PIN 단위로 100% 일치하는지 자동으로 검사한다(EDIF 경로는 [1][2][3] 전부,
   `.DSN`/KiCad 프로젝트 경로는 [3]만 — 7장 참고). 지정하지 않아도 변환 자체는 되지만,
   넷이 맞는지 확인할 방법이 없어진다.

### 4.4 PADS Layout ASCII 보드 (선택) — 풋프린트 매핑 + 보드 대조용

회로도의 부품 Footprint 필드를 실제 보드에서 쓴 데칼(decal)로 채우고, KiCad PCB Editor에서
바로 "Update PCB from Schematic"을 쓸 수 있게 하려면 실제 배선된 PADS 보드가 필요하다.

1. PADS Layout에서 대상 보드(.pcb)를 연다.
2. `File → Export → ASCII...`
3. 익스포트 옵션에서:
   - **전 섹션(all sections)을 포함**한다(부품/넷/패드/실크 등 일부만 내보내면 임포트가
     불완전해진다).
   - **최신 버전(latest version)** 포맷을 선택한다.
   - 단위는 **mm**로 맞춘다(다른 단위면 kicad-cli 임포트 결과 좌표가 틀어질 수 있다).
   - **카퍼 포어(copper pour)를 반드시 포함**하도록 설정한다. PADS ASCII 익스포트는
     기본 설정에 따라 폴리곤 채움 정보(`POUR_OUTLINES`)를 빼고 내보낼 수 있는데, 이 경우
     kicad-cli로 임포트한 보드에는 GND 등 폴리곤으로 접속됐어야 할 패드가 전부
     "미접속(unconnected)"으로 잡혀 DRC를 신뢰할 수 없게 된다(12장 "알려진 제한" 참고).
4. 결과 `.asc` 파일을 `--board`/GUI의 "PADS 레이아웃 ASCII 또는 KiCad PCB"에 지정한다. 이미 KiCad로 임포트해
   둔 `.kicad_pcb`가 있으면 그 파일을 그대로 지정해도 된다(다시 임포트하지 않고 그대로
   읽는다).

## 5. GUI 사용법

실행: `python -m orcad2kicad` (소스) 또는 `orcad2kicad.exe` (exe). 창은 위쪽 입력/AI
영역과 아래쪽 결과 탭(Notebook)으로 나뉜다.

**언어**: "입력" 프레임 오른쪽 위에 "언어: 한국어/English" 콤보박스가 있다. 처음 실행하면
OS 로캘이 한국어(`ko*`)면 한국어, 아니면 영어로 자동 선택되고, 이후 고른 언어는
`settings.json`에 저장되어 다음 실행에도 유지된다. 콤보에서 다른 언어를 고르면 재시작 없이
창 전체(라벨·탭 이름·표 헤더·대화상자 등)가 즉시 새 언어로 다시 그려지고, 마지막 변환 결과와
보드 차이 표에서 고른 처리는 그대로 유지된다. 로그 탭에 흐르는 파이프라인 진행 메시지는
언어와 무관하게 항상 영문(콘솔과 동일)이다.

[스크린샷: 메인 창 전체 — 위쪽 '입력' 프레임(맨 위 '입력 종류' 라디오 EDIF/OrCAD .DSN/KiCad
프로젝트, 그 아래 EDIF·`.DSN`·KiCad 프로젝트 파일 칸 3개(선택한 종류만 활성화), 넷리스트/보드/
출력 폴더/프로젝트/kicad-cli 경로, [나이틀리 KiCad 포터블 준비(설치 없음)] 버튼과 회색 안내문,
넷 이름 라디오·PDF·strict 체크), 그 아래 'AI 에이전트' 프레임, '변환 실행' 버튼과 진행 막대,
아래쪽 6개 탭(로그/검증/이슈/보드 차이/에이전트 제안/결과) — 입력 종류로 'OrCAD .DSN'을 골라
`.DSN` 칸만 활성화된 상태로 변환이 끝나 상태 줄에 '완료 (모든 검증 PASS)'가 뜬 상태]

### 5.1 입력 영역

맨 위 **"입력 종류"** 라디오(EDIF / OrCAD `.DSN` (KiCad 나이틀리 필요) / KiCad
프로젝트(`.kicad_pro`))에서 고른 쪽의 파일 칸만 활성화되고 나머지 두 칸은 회색으로
비활성화된다(3개 중 정확히 하나만 파이프라인에 전달된다 — 1장·0장 참고).

| 항목 | 설명 |
|---|---|
| 입력 종류 | EDIF / OrCAD `.DSN` / KiCad 프로젝트(`.kicad_pro`) 중 라디오로 선택. 기본값 EDIF. 아래 세 파일 칸 중 선택된 종류의 칸만 입력·찾기 버튼이 활성화된다. |
| EDIF 파일 | 4.2절에서 만든 `.EDF`. "입력 종류: EDIF"일 때만 활성화, 그때는 필수 — 비어 있으면 실행 버튼이 경고를 낸다. |
| OrCAD `.DSN` 파일 | 4.1절의 `.DSN`. "입력 종류: OrCAD `.DSN`"일 때만 활성화(권장 경로). 나이틀리 kicad-cli가 없으면 실행 시 오류로 안내된다. |
| KiCad 프로젝트(`.kicad_pro`) | 이미 KiCad로 임포트해 둔 프로젝트. "입력 종류: KiCad 프로젝트"일 때만 활성화. |
| PADS 넷리스트(.asc) | 4.3절. 비우면 [1][2](EDIF 입력만)/[3] 검증 탭이 비어 있다는 안내만 나온다. |
| PADS 레이아웃 ASCII 또는 KiCad PCB | 4.4절. PADS Layout에서 Export ASCII로 내보낸 배선된 보드 파일. `.asc` 또는 `.kicad_pcb`. 비우면 [4] 보드 대조와 풋프린트 매핑을 건너뛴다. |
| 출력 폴더 | KiCad 프로젝트를 쓸 폴더(없으면 새로 만든다). 입력 파일(EDIF/`.DSN`/`.kicad_pro` 중 선택된 것)을 고르면 비어 있을 때 `<입력 파일 폴더>\<이름>_kicad` 가 자동으로 들어간다(프로젝트 이름도 파일 이름으로, 같은 폴더에 이름이 맞는 PADS 넷리스트/보드 `.asc` 가 머리글로 판별돼 있으면 그 칸도 채운다 — 이미 적힌 값은 건드리지 않음). EDIF 입력에서 이 칸을 지우면 파일을 쓰지 않고 검증만 한다(콘솔 도구의 `-o` 생략과 동일). `.DSN`/KiCad 프로젝트 입력은 비워도 같은 기본 폴더(`<입력 파일 폴더>\<이름>_kicad`)에 쓴다 — 검증만 하는 모드가 없다. |
| 프로젝트 이름 | 비우면 EDIF 입력은 설계 이름, KiCad 프로젝트/`.DSN` 입력은 입력 `.kicad_pro`/`.DSN` 파일 이름을 그대로 쓴다. |
| kicad-cli 경로 | 비우면 자동 탐지한 경로를 시작할 때 채워 넣는다. 여러 버전이 설치돼 있으면 여기서 강제 지정(정식/나이틀리 어느 쪽이든 지정 가능 — 무엇이 필요한지는 아래 안내문·0장 참고). |
| [나이틀리 KiCad 포터블 준비(설치 없음)] 버튼 | 최신 KiCad 나이틀리를 설치 없이 압축만 풀어 준비하고, 끝나면 위 "kicad-cli 경로" 칸을 자동으로 채운다(0장). 옆의 회색 안내문 **"나이틀리(10.99+)는 .DSN 임포트에만 필요. 결과는 정식 KiCad 10.0 포맷으로 저장됨"**이 언제 나이틀리가 필요한지 알려준다 — EDIF나 이미 임포트된 KiCad 프로젝트만 쓴다면 이 버튼을 누를 필요가 없다. |
| 넷 이름: 자동/보드 이름 유지(keep)/KiCad 방식 | "자동"은 보드를 지정했으면 `keep`, 아니면 `kicad`를 쓴다. `keep`은 PADS 넷 이름을 그대로 전역 라벨로 남겨 보드와 이름이 계속 맞물리게 한다(보드 연동 시 권장). `kicad` 모드는 KiCad가 알아서 `Net-(...)` 식 이름을 붙인다. `.DSN`/KiCad 프로젝트 입력은 임포트된 회로도가 이미 전역 라벨을 쓰므로 이 선택과 무관하게 항상 `keep`으로 동작한다(로그에 안내가 남는다). |
| PDF 출력 | 체크하면 kicad-cli로 회로도 PDF도 함께 뽑는다. |
| 보드 차이 엄격(strict) | 체크하면 [4] 보드 vs 회로도 대조가 실패(FAIL)이거나 레퍼런스가 다르면 실행 결과를 실패(종료 코드 1)로 취급한다. 기본은 정보 표시만 하고 성공으로 끝낸다. |

"변환 실행" 버튼을 누르면 별도 스레드에서 파이프라인이 돌고(창이 멈추지 않는다),
진행 로그가 "로그" 탭에 실시간으로 쌓인다. 끝나면 상태 줄에 `완료 (모든 검증 PASS)` /
`완료 (검증 FAIL 있음)` / `오류 (입출력/kicad-cli)` 중 하나가 뜬다.

입력값은 창을 닫을 때(또는 실행할 때) `~/.orcad2kicad/settings.json`에 저장되어 다음 실행
때 그대로 복원된다(**API 키는 저장하지 않는다** — 8장 참고). 경로는 환경변수
`O2K_SETTINGS`로 바꿀 수 있다.

### 5.2 결과 탭

- **로그**: 파이프라인/에이전트가 내보내는 진행 메시지(영문, 콘솔과 동일). 실행이 끝나면
  맨 아래에 "결과" 탭과 같은 **요약 설명(한국어)**이 그대로 이어 붙는다(스크롤해서 다시
  볼 수 있음).
- **검증**: PADS 넷리스트를 줬을 때 [1] EDIF 조인 vs PADS, [2] 지오메트리 vs PADS,
  kicad-cli가 있으면 [3] kicad-cli 넷리스트 vs PADS까지 각각 요약 줄 + 넷별 표로 보여준다.
  표의 상태 열은 `OK`/`DIFF`/`ONLY_OURS`/`ONLY_REF`다(7장에서 의미 설명). `.DSN`/KiCad
  프로젝트 입력 모드는 EDIF가 없어 [1][2]가 없다 — 탭 맨 위에 회색 글씨로
  `[1][2] EDIF 없음 — 건너뜀` 안내가 뜬다.
- **이슈**: 변환 중 감지된 이슈(파싱 시 지원하지 않는 구성, writer 경고, 보드 매핑 메모
  등) 목록. 위 입력창에 문자열을 입력하면 부분 일치(대소문자 무시)로 실시간 필터링된다.
- **보드 차이**: [4] 보드 vs 회로도 대조 결과를 표로 보여주고, 행마다 처리 방법을 고를 수
  있다(아래 5.3절).
- **에이전트 제안**: AI 백엔드로 얻은 제안 목록과 체크박스(아래 5.4절).
- **결과**: 맨 위에 **"요약 설명"** 상자, 그 아래 만들어진 파일 목록과 경로.
  - **요약 설명**은 이번 실행을 사람 말로 풀어 쓴 것이다(`explain.py`) — 입력이 무엇이었는지,
    [1][2](해당하면)·[3]·풋프린트 필드 출처·[4]가 각각 무엇을 확인했고 결과가 무엇을
    뜻하는지, ERC 위반을 유형별로 **정보(조치 불필요)/확인 권장/조치 필요**로 나눠 설명,
    출력 파일을 어떤 KiCad로 열어야 하는지, 마지막으로 "결론: 문제 없음" 또는 "결론: 확인할
    항목 있음 - ..." 한 줄로 끝난다. `.DSN`/KiCad 프로젝트 입력 모드면 [1][2]가 없다는 것과
    `.DSN`을 쓴 경우 나이틀리가 언제만 필요한지도 여기서 함께 설명된다. `.DSN`/KiCad 프로젝트
    입력 모드에서는 이 상자 위에 검증 탭과 같은 `[1][2] EDIF 없음 — 건너뜀` 안내도 함께 뜬다.
  - 파일 목록에는 루트 회로도, 심볼 라이브러리(`orcad_import.kicad_sym` 등), `.kicad_pro`,
    보드, PDF, ERC 결과 JSON, kicad-cli 넷리스트 등이 만들어진 것만 나온다.
  - **"결과 폴더 열기"**는 출력 폴더를 탐색기로 연다.
  - **"KiCad 프로젝트 열기"**는 `.kicad_pro`를 연다 — 회로도 포맷이 정식 KiCad 10.0의 상한
    (20260306)을 넘으면(`--nightly-format`을 줘서 나이틀리 원본 포맷을 그대로 남긴 경우)
    파일 연결 프로그램(설치된 정식 KiCad)으로는 안 열리므로, 이 버튼이 자동으로 kicad-cli
    옆의 포터블 나이틀리 `kicad.exe`를 찾아 그것으로 직접 띄운다. 포터블 나이틀리를 아직
    준비하지 않았으면 "나이틀리 KiCad 필요" 경고와 함께 입력 프레임의 준비 버튼을 안내한다.
    기본값(재구성됨, 포맷 20260306)이면 그냥 파일 연결 프로그램으로 열리므로 이 문제 자체가
    생기지 않는다.

### 5.3 "보드 차이" 탭에서 불일치 해소하기

`--board`를 줬을 때만 채워진다. 표의 각 행은 아래 5종류 중 하나이고, 행을 선택하면
아래 콤보박스에서 처리 방법을 고를 수 있다.

[스크린샷: '보드 차이' 탭 — 종류/대상/상세/처리 4열 표에 '보드 전용 부품 J19·J20',
'풋프린트 이름 차이 U7~U10', '보드 패드에 없는 핀 H1~H4' 행이 보이고, J19 행을 선택해 아래
콤보박스가 '회로도에 추가'로 바뀐 상태 + '적용 후 재출력' 버튼]

| 종류(표시명) | 뜻 | 선택지 | 선택의 의미 |
|---|---|---|---|
| 보드 전용 부품 | 보드에는 있는데 회로도에 없는 레퍼런스(예: J19, J20) | 무시 / 회로도에 추가 | "회로도에 추가"를 고르면 재실행 시 `99-PCB-ONLY`라는 별도 페이지에 그 레퍼런스의 자리표시 심볼(핀 이름만 있는 최소 심볼)을 만들어 붙인다. 실물 부품이 맞는데 회로도 갱신이 늦은 경우에 쓴다. "무시"를 고르면 다음 재실행에서도 계속 표에 나타난다(정말 없애려면 보드에서 부품을 지우거나 회로도에 반영해야 한다). |
| 회로도 전용 레퍼런스 | 회로도에는 있는데 보드 부품에 없는 레퍼런스 | 무시 / 리포트에서 숨김 | "리포트에서 숨김"은 다음 [4] 리포트에 이 레퍼런스를 더 이상 보여주지 않는다(실제로 부품을 지우거나 추가하는 게 아니라 **보고만 숨기는** 것 — 기구 부품처럼 원래 보드에 없는 게 정상인 항목에 쓴다). |
| 풋프린트 이름 차이 | 같은 레퍼런스인데 OrCAD Footprint 필드와 보드 데칼 이름이 다름(예: U7~U10 SO8 vs SO8NB) | 보드 / OrCAD | "보드"(기본)는 재출력 시 보드 쪽 데칼을 그대로 쓴다(실제 배선된 PCB 기준이므로 보통 이쪽이 맞다). "OrCAD"를 고르면 회로도 Footprint 필드 값을 우선한다 — 보드가 구버전이거나 회로도 쪽이 최신 설계 의도인 경우에 쓴다. |
| 보드 패드에 없는 핀 | 회로도 핀 번호가 보드 풋프린트 패드에는 없음(예: H1~H4의 핀 1) | 무시 / 리포트에서 숨김 | 넷이 없는 핀(마운팅 홀 등)일 때가 많다 — 실제 배선에는 영향 없으므로 보통 "리포트에서 숨김"으로 정리한다. |
| 넷 차이 | 기준 넷리스트/보드 사이의 넷 불일치(DIFF/보드에만 있는 넷/기준에만 있는 넷) | 무시(선택지 없음) | 정보 표시용이다. 회로도나 보드 배선 자체를 고쳐야 하는 문제라 이 표에서 직접 해소할 수 없다 — 어떤 넷인지 확인하고 KiCad/PADS에서 직접 배선을 바로잡을 것. |

행을 원하는 대로 고른 뒤 **"적용 후 재출력"**을 누르면 현재 표의 선택 상태를
`Resolutions`의 네 필드(`add_board_only_parts` = 회로도에 추가할 보드 전용 레퍼런스,
`footprint_choice` = 레퍼런스별 풋프린트 출처, `pin_type_overrides` = 라이브러리 핀 전기 타입,
`ignore_refs` = 리포트에서 숨길 레퍼런스)로 변환해 파이프라인을 다시 돌린다 — 즉 출력 폴더의
파일이 새로 씌워진다. 표에서 고를 수 있는 것은 이 중 세 가지고, `pin_type_overrides`는
에이전트 제안(5.4절)이나 CLI `--pin-type`으로만 들어온다.

"적용 후 재출력"은 **여러 번 눌러도 안전하다.** '회로도에 추가'로 이미 해소한 부품은 다음
[4] 리포트의 "보드에만 있는 레퍼런스"에서 빠지지만, 표에는 처리가 '회로도에 추가'인 행으로
그대로 남는다 — 그래서 두 번째 재출력에서도 결정이 유지되고(자리표시 페이지가 사라지지
않는다), 마음이 바뀌면 그 행을 '무시'로 되돌릴 수 있다.

또한 보드 전용 자리표시 부품이 하나라도 있으면 넷 이름 모드가 자동으로 `keep`으로 강제된다
(자리표시 심볼은 전역 라벨로만 넷에 붙기 때문). 이때 위쪽 '넷 이름' 라디오도 `keep`으로 함께
바뀌고 로그 탭에 `net names: pipeline used keep (selected kicad)` 한 줄이 남는다 — 화면 선택과
실제 결과가 어긋나지 않게 하기 위한 것이다.

이 결정은 GUI를
껐다 켜도 다음 실행에는 남아 있지 않는다(설정 파일에는 입력 경로만 저장되고 `Resolutions`
자체는 저장되지 않는다) — 같은 결정을 계속 쓰려면 CLI의 `--add-board-part` /
`--footprint-choice` / (해당 시) 코드에서 직접 넘기는 방법을 쓴다.

### 5.4 "에이전트 제안" 탭에서 AI 제안 쓰기

[스크린샷: '에이전트 제안' 탭 — 선택/에이전트/종류/대상/내용/근거/확신 7열 표에 핀 타입
제안(선택 칸 `[ ]`)과 넷·보드 차이 제안(선택 칸 `[v]`)이 섞여 있고, 아래 '리뷰 요약' 상자에
한국어 마크다운 요약이 들어찬 상태 + '제안 생성' / '선택 적용 후 재출력' 버튼]

1. 먼저 "AI 에이전트" 영역에서 백엔드를 고르고(8장), 옆의 상태 문구가 "사용 가능"인지
   확인한다.
2. 돌릴 에이전트(핀 타입/넷·보드 차이/리뷰 요약)를 체크한다(기본 모두 체크).
3. "제안 생성" 버튼(AI 영역 또는 에이전트 제안 탭 안 모두 같은 동작)을 누르면 마지막
   변환 결과를 입력으로 에이전트가 실행되고, 표에 제안이 쌓인다.
4. 표의 "선택" 칸을 클릭하면 체크가 토글된다. **핀 타입 제안은 기본 미선택**이다(핀
   전기 타입은 넷 연결에 영향을 주지 않지만 잘못 채우면 ERC 경고 성격이 바뀌므로,
   사람이 한 번 훑어보고 고르라는 의도). 다른 종류(보드 전용 부품 추가, 풋프린트 선택)는
   기본 선택된 상태로 나온다.
5. **"선택 적용 후 재출력"**을 누르면 체크된 제안만 `Resolutions`/핀 타입 오버라이드로
   반영한 뒤 파이프라인을 다시 돌린다. 적용할 수 없는 제안(목록에 없는 핀 타입, 빈
   레퍼런스 등)은 조용히 버려진다.
6. "리뷰 요약" 상자에는 리뷰 에이전트가 만든 한국어 마크다운 요약(검증 결과, ERC, 남은
   위험 요약)이 표시된다 — 적용 대상이 아니라 참고용 텍스트다.

## 6. CLI 사용법

실행: 소스에서는 `python -m orcad2kicad.cli ...`(PYTHONPATH에 `src` 필요), exe에서는
`orcad2kicad-cli.exe ...`.

### 6.1 옵션 전체 표

`PYTHONPATH=src python -m orcad2kicad.cli --help`로 직접 확인한 내용(2026-09-09 기준,
버전이 올라가면 재확인할 것):

| 옵션 | 의미 | 기본값 |
|---|---|---|
| `edf` (위치 인자) | OrCAD EDIF 2.0.0 익스포트 파일 경로. `--kicad-project`/`--dsn` 중 하나를 쓸 때는 생략(셋 중 정확히 하나만 지정) | — |
| `--kicad-project PRO` | 입력으로 쓸 기존 KiCad 프로젝트(`.kicad_pro`, 예: `.DSN`을 KiCad에서 직접 임포트해 둔 것). EDIF가 없으므로 [1][2] 검증은 건너뛴다(0장 "OrCAD 없이 변환하기" 참고) | 없음 |
| `--dsn FILE` | OrCAD `.DSN` 파일. kicad-cli(**KiCad 나이틀리 10.99+ 필요**)의 네이티브 임포터로 변환한 뒤 `--kicad-project`와 같은 경로로 이어진다 | 없음 |
| `--netlist NETLIST` | 기준 PADS2000 `.asc` 넷리스트 | 없음(주면 [1][2] 검증 실행) |
| `--report REPORT` | 리포트 텍스트를 이 파일에도 저장 | 없음(stdout만) |
| `--explain` | 리포트 끝에 요약 설명을 붙인다 — 각 검증이 무엇을 확인했고 결과가 무엇을 뜻하는지, ERC 유형별 의미와 조치 필요 여부, 결과 파일을 어떤 KiCad 로 열어야 하는지(영문). GUI 는 같은 내용을 한국어로 결과 탭과 로그 끝에 항상 보여 준다. | 꺼짐 |
| `--issues` | 감지된 이슈 전체를 출력 | 꺼짐(요약 줄의 개수만 표시) |
| `-o, --outdir OUTDIR` | KiCad 프로젝트를 쓸 폴더 | 없음(주면 파일을 실제로 씀) |
| `--project PROJECT` | 프로젝트 이름 | EDIF 설계 이름 |
| `--kicad-cli KICAD_CLI` | kicad-cli 실행 파일 경로 | 자동 탐지 |
| `--pdf` | kicad-cli로 회로도 PDF도 출력 | 꺼짐 |
| `--board BOARD` | PADS 보드(`.asc`는 kicad-cli로 임포트, `.kicad_pcb`는 그대로 읽음) | 없음 |
| `--net-names {kicad,keep}` | 넷 이름 부여 방식 | `--board` 있으면 `keep`, 없으면 `kicad` |
| `--strict-board` | [4] 보드 vs 회로도 비교가 FAIL이거나 레퍼런스가 다르면 종료 코드 1 | 꺼짐(정보만 출력, 종료 코드에 영향 없음) |
| `--nightly-format` | `--kicad-project`/`--dsn` 전용. 나이틀리 임포터 결과를 정식 KiCad 10.0 포맷(루트 시트 + 하위 시트, 3단계-C-2)으로 재구성하지 **않고** 나이틀리 원본 그대로 둔다(그 결과를 열고 [3]/ERC 를 돌리려면 나이틀리 kicad-cli 가 다시 필요해진다) | 꺼짐(기본은 항상 정식 포맷으로 재구성) |
| `--add-board-part REF` | 보드 전용 레퍼런스를 회로도에 자리표시 심볼로 추가(반복 지정 가능) | 없음 |
| `--footprint-choice REF=board\|orcad` | 레퍼런스별 풋프린트 출처 선택(반복 지정 가능) | 지정 없는 레퍼런스는 `board` |
| `--pin-type SYMBOL:PIN=TYPE` | 라이브러리 핀 전기 타입 오버라이드(예: `STM32H723ZGT6:6=power_out`, 반복 지정 가능) | 없음 |
| `--fetch-kicad-nightly [DIR]` | **변환과는 별개 동작.** 최신 KiCad 나이틀리 설치본을 받아 **압축만 풀어**(설치기는 실행하지 않는다) 포터블 kicad-cli를 준비하고 그 경로를 찍은 뒤 끝낸다. 압축 도구는 **없어도 된다** — 7-Zip/Bandizip이 없으면 7-Zip 콘솔판(약 6 MB)을 공식 사이트에서 받아 역시 압축 해제만 해서 쓴다(설치하지 않음). Windows 전용. 0장 참고 | `DIR` 기본값 `%LOCALAPPDATA%\orcad2kicad\kicad-nightly` |
| `--kicad-nightly-installer FILE` | `--fetch-kicad-nightly`와 함께: 이미 받아 둔 나이틀리 설치본을 쓴다(네트워크 접속 없음) | 없음(내려받음) |
| `--force-fetch` | `--fetch-kicad-nightly`와 함께: 이미 준비돼 있어도 지우고 다시 푼다(나이틀리 갱신) | 꺼짐 |
| `--no-download-tools` | `--fetch-kicad-nightly`와 함께: 압축 도구가 없을 때 7-Zip 콘솔판을 받아 오지 **않고** 안내와 함께 실패한다 | 꺼짐(없으면 받아서 압축만 품) |

`--add-board-part`/`--footprint-choice`/`--pin-type`는 **`edf` 입력에서만 지원**된다.
`--kicad-project`/`--dsn` 입력에서는 이슈 한 줄만 남기고 무시된다(맨 위 새 절 "제한" 참고).

### 6.2 예시

**1) 검증만(파일을 쓰지 않음, 1·2차)**

bash:
```bash
PYTHONPATH=src python -m orcad2kicad.cli MYBOARD.EDF \
  --netlist MYBOARD.asc --issues
```
PowerShell:
```powershell
$env:PYTHONPATH = 'src'
python -m orcad2kicad.cli MYBOARD.EDF `
  --netlist MYBOARD.asc --issues
```

**2) KiCad 출력 포함(1·2·3차 검증 + ERC + PDF)**

bash:
```bash
PYTHONPATH=src python -m orcad2kicad.cli MYBOARD.EDF \
  -o out/kicad --project MYBOARD \
  --netlist MYBOARD.asc --pdf --issues
```
PowerShell:
```powershell
python -m orcad2kicad.cli MYBOARD.EDF `
  -o out/kicad --project MYBOARD `
  --netlist MYBOARD.asc --pdf --issues
```

**3) PADS 보드 연동(풋프린트 매핑 + [4] 대조까지)**

bash:
```bash
PYTHONPATH=src python -m orcad2kicad.cli MYBOARD.EDF \
  -o out/kicad --project MYBOARD \
  --netlist MYBOARD.asc \
  --board MYBOARD_board.asc --pdf --issues
```
PowerShell:
```powershell
python -m orcad2kicad.cli MYBOARD.EDF `
  -o out/kicad --project MYBOARD `
  --netlist MYBOARD.asc `
  --board MYBOARD_board.asc --pdf --issues
```

**4) 불일치 해소 옵션을 CLI에서 바로 지정**

```bash
PYTHONPATH=src python -m orcad2kicad.cli MYBOARD.EDF \
  -o out/kicad --project MYBOARD \
  --netlist MYBOARD.asc \
```

`--strict-board`에서 [4]가 FAIL) / 2(입력을 못 읽거나 출력을 못 쓰거나 kicad-cli 실행
자체가 실패)이다.

## 7. 검증 결과 읽는 법

변환기는 최대 4단계로 "우리가 만든 넷 연결"과 "정답(기준)"을 비교한다. 전부 REF.PIN
집합(어떤 부품 어떤 핀들이 한 넷에 물려 있는가) 기준이며, **넷 이름이 달라도 REF.PIN
집합이 같으면 같은 넷으로 본다**(정답 파일에 이름이 없는 넷도 많기 때문).

| 단계 | 비교 대상 | kicad-cli 필요? | 의미 |
|---|---|---|---|
| [1] EDIF 조인 vs PADS | EDIF의 연결 정보(핀-넷 연결 그래프)를 직접 조인해 만든 넷 vs `--netlist` | 아니오 | 리더가 EDIF를 올바르게 해석했는지 |
| [2] 지오메트리 vs PADS | 회로도 도형(와이어·핀 좌표)에서 기하학적으로 유도한 넷 vs `--netlist` | 아니오 | 좌표/와이어 연결 처리가 올바른지(리더 결과와 별개 경로로 재확인) |
| [3] kicad-cli 넷리스트 vs PADS | 실제로 쓴 `.kicad_sch`를 kicad-cli로 넷리스트 export한 결과 vs `--netlist` | 예 | **최종 산출물**이 KiCad에서도 같은 넷으로 읽히는지(포맷 버그가 있으면 여기서만 잡힌다) |
| [4] 보드 vs 회로도 | `--board`로 읽은 PCB 넷 vs 위 기준(`--netlist`가 없으면 kicad-cli로 뽑은 회로도 넷리스트가 기준 — 리포트 제목이 `board pad nets vs schematic netlist`) | .asc면 예, .kicad_pcb면 아니오 | 실제 배선된 보드와 회로도가 일치하는지(부품/풋프린트/핀 매칭까지) |

각 단계 결과는 아래 상태로 나뉜다(GUI "검증" 탭의 상태 열, CLI 리포트 텍스트 동일):

- **PASS / OK** — 그 넷(또는 단계 전체)이 정답과 완전히 일치.
- **DIFF** — 같은 이름/집합으로 짝지어진 넷인데 REF.PIN이 다르다(우리 쪽에만 있는 핀 =
  missing 아님, `missing`은 "기준에는 있는데 우리한테 없는 것", `extra`는 그 반대다 —
  GUI 표의 "기준에만(missing)"/"우리에만(extra)" 열 이름 참고).
- **ONLY_OURS** — 우리 출력에만 있고 기준에는 없는 넷(기준 넷리스트가 이 넷을 모르거나,
  우리가 잘못 나눈 경우).
- **ONLY_REF** — 기준에는 있는데 우리 출력에는 없는 넷(연결이 통째로 빠진 경우 — 가장
  심각한 부류).

리포트 마지막 줄의 `RESULT: PASS`/`RESULT: FAIL`은 그 단계에 속한 모든 넷이 OK일 때만
PASS다. 종료 코드 1은 [1][2][3] 중 하나라도 FAIL이면 뜬다([4]는 `--strict-board`를 줘야
종료 코드에 영향을 준다 — 회로도/보드가 서로 다른 시점의 설계를 반영하는 경우가 흔해서
기본은 정보 표시로만 그친다).

**ERC 요약 줄**(`erc violations: N ...`)은 KiCad ERC(Electrical Rules Checker) 결과
개수다. 위반 종류별 세부는 `erc.json`(GUI "결과" 탭에서 경로 확인)에 있다. 이 숫자는
넷 연결 정확성과는 별개다 — 예를 들어 풋프린트 필드가 비어 있으면(보드 없이 변환한 경우)
`footprint_link_issues`가 부품 수만큼 뜨지만 넷 연결 자체는 정확할 수 있다.

예시 보드(9페이지, 134넷, 187부품) 실측:

| 실행 | ERC 위반 | 내역 |
|---|---|---|
| `--board` 없이 | **295건** | `footprint_link_issues=191`, `different_unit_footprint=2`, `pin_not_connected=63`, `unconnected_wire_endpoint=23`, `power_pin_not_driven=12`, `isolated_pin_label=2`, `pin_not_driven=2` |
| `--board` 지정 | **102건** | `footprint_link_issues` **0건**(풋프린트가 PADS 라이브러리로 채워지므로 사라진다), 나머지는 위와 동일 |

즉 `--board` 없이 뜨는 위반의 대부분(191/295)은 "풋프린트가 비어 있다"는 것 하나이고, 넷
연결과는 무관하다. 남는 102건은 미사용 핀·미결선 와이어 끝점 등 원본 회로도에서 그대로
넘어온 것이다. `--add-board-part`로 자리표시 부품을 추가하면 그 심볼의 미결선 핀만큼 몇 건
더 늘어난다.

## 8. AI 백엔드 설정

**AI는 항상 선택 사항이다.** 백엔드가 없어도(기본값 `없음`) 변환·검증·KiCad 출력은
전부 완전히 동작한다. AI는 "핀 타입 제안", "보드/회로도 차이 해소 제안", "결과 리뷰
요약" 세 가지만 만들고, 적용 여부는 항상 GUI 표에서 사람이 고른다(5.4절).

| 백엔드 | 설정 방법 | 비용 | 비밀 유지 |
|---|---|---|---|
| `없음`(기본) | 아무것도 안 해도 됨 | 없음 | 아무 데이터도 밖으로 나가지 않음 |
| `api` (Anthropic API 직접 호출) | 환경변수 `ANTHROPIC_API_KEY`를 설정하거나 GUI의 "API 키" 칸에 붙여넣기(칸에 넣은 값은 **저장되지 않는다** — 창을 닫으면 사라지고 다음 실행 때 다시 환경변수 기본값만 채워진다). CLI/스크립트에서 직접 쓰려면 `agents.make_backend('api', api_key=..., model=...)`. | 토큰 사용량만큼 Anthropic에 과금(호출당 회로도 요약·이슈 목록·핀 목록 정도 크기, 대형 설계라도 한 번에 수 KB 수준). | **회로도 설계 데이터(부품명·핀 이름·넷 차이 등)가 Anthropic API로 전송된다.** 사내 기밀 설계라면 이 백엔드를 쓰기 전에 데이터 반출 정책을 확인할 것. |
| `claude-cli` (로컬 Claude Code CLI) | PC에 Claude Code(`claude`)가 설치·로그인돼 있어야 한다(구독 인증 재사용, API 키 불필요). `claude -p ... --output-format json`을 내부적으로 호출. | 구독 요금제 안에서 소비(별도 API 과금 없음, 단 사용량 한도는 계정 정책에 따름). | 마찬가지로 설계 데이터가 Anthropic 서비스로 전송된다(경유 경로만 API 대신 CLI/구독). |
| `codex-cli` (실험적) | PC에 OpenAI Codex CLI(`codex`)가 설치돼 있어야 한다(`codex exec ...` 호출). 이 PC 기준 미설치 상태로 실측하지 못했다 — 동작은 코드 리뷰 수준으로만 확인됨. | Codex CLI/계정 정책에 따름. | 설계 데이터가 OpenAI 서비스로 전송된다. |

GUI에서는 백엔드를 고르면 옆에 "사용 가능: ..." 또는 "사용 불가: 이유"가 바로 뜬다(예:
`ANTHROPIC_API_KEY not set`, `claude CLI not found in PATH`). CLI/MCP에서는 환경변수
`O2K_AGENT_BACKEND`(`none`/`api`/`claude-cli`/`codex-cli`)로 기본 백엔드를 지정할 수
있다(MCP `suggest` 툴 참고, 9장).

> **참고**: `api` 백엔드는 이 PC에 API 키가 없어 실제 호출 경로(HTTP 요청/응답 파싱)를
> 라이브 테스트하지 못했다 — 코드 리뷰와 오류 처리 경로(`FakeBackend`를 쓴 단위 테스트)
> 로만 확인됨. API 키가 있는 환경에서 실제로 한 번 확인해 보는 것을 권장한다.

## 9. MCP 서버 등록

MCP(Model Context Protocol) 서버는 Claude Code 같은 외부 AI 도구가 이 변환기를 툴로
직접 호출할 수 있게 해 준다(stdio, JSON-RPC 2.0, 표준 라이브러리만으로 구현 — SDK
의존 없음).

### 9.1 Claude Code에 등록

```bash
# 소스에서 바로 (PYTHONPATH에 src를 넣어야 orcad2kicad 패키지가 보인다)
claude mcp add orcad2kicad -e PYTHONPATH=<repo>/src -- python -m orcad2kicad.mcp_server

# 셸에서 PYTHONPATH를 이미 잡아 둔 경우
claude mcp add orcad2kicad -- python -m orcad2kicad.mcp_server

# 단일 exe로 배포한 경우
claude mcp add orcad2kicad -- orcad2kicad-cli.exe --mcp
```

### 9.2 설정 JSON으로 직접 등록하는 경우 (예시)

```json
{
  "mcpServers": {
    "orcad2kicad": {
      "command": "orcad2kicad-cli.exe",
      "args": ["--mcp"]
    }
  }
}
```

소스 실행판이면:
```json
{
  "mcpServers": {
    "orcad2kicad": {
      "command": "python",
      "args": ["-m", "orcad2kicad.mcp_server"],
      "env": { "PYTHONPATH": "<repo>/src" }
    }
  }
}
```

### 9.3 실행 옵션

- `--root DIR` — `read_file` 툴이 읽을 수 있는 루트 디렉터리(여러 번 지정 가능).
  환경변수 `O2K_MCP_ROOT`(`os.pathsep` 구분, 즉 Windows는 `;`)로도 지정할 수 있다.
  지정하지 않으면 가장 최근 `convert` 호출의 출력 폴더만 읽을 수 있다.
- `--selftest` — 툴 목록을 JSON으로 출력하고 즉시 종료(exit 0). 설치 확인/패키징
  스모크 테스트용. 예: `PYTHONPATH=src python -m orcad2kicad.mcp_server --selftest`.

**`convert`에 넘긴 `outdir`은 그 뒤로 `read_file`의 허용 루트가 된다.** 즉 `--root`를 하나도
주지 않아도, 변환을 한 번 돌리고 나면 AI가 그 출력 폴더 안의 `.kicad_sch`/`erc.json`/
넷리스트를 바로 읽어 볼 수 있다(그 폴더 밖은 여전히 거부된다).

### 9.4 제공 툴 목록 (`tools/list`, 실측)

| 툴 | 하는 일 | 파일을 씀? |
|---|---|---|

| `list_issues` | 이 세션에서 가장 최근에 실행한 convert/verify/board_diff가 남긴 이슈 목록 | 아니오 |
| `read_file` | 변환 결과 폴더(또는 `--root`) 안의 텍스트 파일을 읽는다(`.kicad_sch`, `erc.json`, 넷리스트 등). `..` 경로 탈출은 거부. | 아니오 |

| `prepare_kicad_nightly` | 나이틀리 kicad-cli를 **설치 없이** 준비한다(공식 설치본 다운로드 → 압축 해제 → 정리 → 실행 확인). 인자 `root`/`installer`/`force`/`download_tools` 전부 선택. 설치 프로그램(KiCad·7-Zip 어느 쪽이든)은 실행하지 않는다. 압축 도구가 없으면 7-Zip 콘솔판을 받아 압축만 풀어 쓴다(`download_tools: false`면 대신 실패) | 예(첫 호출 수 분, 약 234 MB 다운로드. 두 번째부터는 즉시) |

주의: 파이프라인은 동기 실행이라 `convert` 한 번이 끝날 때까지 서버는 다음 요청을 읽지
않는다(동시에 여러 convert를 보낼 수 없다 — 12장 참고). 진행 상황은 stderr 로그로 확인.

## 10. KiCad에서 마무리

자동 검증은 **넷 연결이 정답과 일치하는지**만 확인한다. 심볼 모양·회전·텍스트 겹침 같은
육안 확인, 그리고 실제 PCB에 "Update PCB from Schematic"을 적용했을 때의 동작은 사람이
KiCad GUI에서 직접 확인해야 한다.

**어느 입력 경로든 열어서 확인하는 방법은 같다.** `.DSN`/KiCad 프로젝트 입력의 결과는
기본값(`--nightly-format`을 주지 않은 경우, 0장)으로 정식 KiCad 10.0 포맷(버전 20260306)
- 루트 시트(`<프로젝트>.kicad_sch`) + 페이지별 하위 시트(`P01_...`, `P02_...`, ... — 원래
나이틀리 임포터가 만든 최상위 시트 여러 개를 재구성한 것) 구조로 저장돼 있으므로, EDIF
경로의 결과와 마찬가지로 **정식 KiCad 10.0을 더블클릭으로 열면 그대로 편집·ERC·PCB 갱신이
된다** — 나이틀리는 다시 필요 없다. 페이지별 대조·ERC 무시 목록·Update PCB 절차는
`.DSN`/KiCad 프로젝트 경로 결과에도 그대로 적용된다(시트가 여러 개인 계층 구조라는 점,
풋프린트가 `PADS:<데칼>`로 채워져 있다는 점이 동일하기 때문).

1. **회로도 육안 대조 + ERC** — `.kicad_pro`를 열어 원본 회로도와 페이지 단위로 대조한다.
   ERC 결과 중 격자 이탈(`endpoint_off_grid`), 미접속 표시 없는 와이어 끝점
   (`unconnected_wire_endpoint`), `PWR_FLAG` 없음처럼 임포터 특성·KiCad 관례 차이로 생기는
   항목(7장·12장 설명 참고)은 대부분 무시해도 되고, 그 외 처음 보는 종류의 경고는 해당
   페이지에서 실제 연결을 확인할 것.
2. **PCB Update PCB from Schematic + DRC** — `--board`로 변환했다면, Pcbnew의
   Update PCB from Schematic(F8) 대화상자에서 옵션 체크박스 중 **"Delete footprints with no
   symbols"는 반드시 끈다**(켜져 있으면 보드 전용 부품이 삭제된다). 실행 전 미리보기에서
   추가/삭제/변경될 항목을 확인하고 적용한다. 이어서 DRC를 돌리면 카퍼 포어(copper pour)가
   빠진 PADS ASCII 익스포트 때문에 미접속 경고가 다수 뜰 수 있는데(4.4절·12장 참고), 이는
   실제 배선 오류가 아니라 익스포트 옵션 문제이므로 구분해서 볼 것.

## 12. 알려진 제한

`--dsn`/`--kicad-project` 입력 모드 도입 시점 기준으로 갱신한 목록이다.

- **`--dsn`/`--kicad-project` 입력 모드는 자리표시 부품·풋프린트 선택·핀 타입 오버라이드
  미지원**(0장 "OrCAD 없이 변환하기" 참고) — `edf` 입력에서만 지원된다.
- **나이틀리 임포트 결과의 ERC 잔여 412건**(`endpoint_off_grid` 122,
  `unconnected_wire_endpoint` 177, `pin_not_connected` 63, `same_local_global_label` 26 등)은
  손대지 않았다 — KiCad 임포터 자체의 결과이며 원인 분석은 다음 단계 과제.
- **뒷면(B.Cu)에만 있는 풋프린트는 뒷면 인스턴스를 앞면 정의로 뒤집어 라이브러리에 넣는다**
  (이슈 목록에 `… derived from back-side <REF> (flipped to front)` 로 표시). 패드·실크 좌표와
  레이어를 KiCad 규약대로 되돌리므로 Update PCB 에 그대로 쓸 수 있지만, 특수 패드(모따기 사각
  패드의 모서리 지정 등)는 검토한 사례가 없다. 이상하면 KiCad 풋프린트 편집기에서 확인할 것.
- **H1~H4류 패드 번호 없음** — PADS 보드 임포트 결과 일부 부품의 패드 번호가 빈 문자열로
  들어와 회로도 핀 번호와 못 맞추는 경고가 뜬다(넷이 없는 핀이라 배선에는 영향 없음).
- **보드 전용 부품 자동 추가는 사람이 결정** — J19/J20류를 회로도에 자동으로 추가하지
  않는다(GUI "보드 차이" 탭 또는 `--add-board-part`로 사람이 명시해야 한다).
- **PADS ASCII 익스포트에 카퍼 포어가 없으면 DRC 미접속 다수(샘플 기준 161건)** — 배선
  오류가 아니라 익스포트에 폴리곤 정의 자체가 빠진 것(`POUR_OUTLINES 0`)이 원인. 4.4절
  절차대로 카퍼 포어를 포함해 다시 익스포트하거나 KiCad에서 직접 채워야 DRC를 신뢰할 수
  있다.
- ~~OrCAD 자유 텍스트/심볼 그래픽 텍스트의 `%<10진수>%` 바이트 이스케이프 미복원~~ →
  **3단계-B에서 해결(설명서 기술이 낡았던 것).** `decode_orcad_text`가 연속한 `%NN%`을 모아
  cp949(실패 시 latin-1)로 디코드하고 CR/LF는 줄바꿈으로 되돌린다 — 샘플 회로도에는 이스케이프가
  하나도 남지 않는다. 2026-09-09 추가: 탭/줄바꿈을 뺀 C0 제어문자(`%0%` NUL 등)는 그대로 두면
  `.kicad_sch`를 깨뜨리므로 버린다.
- **미러된 EDIF 표시 방향(MX/MY/MXR90/MYR90) 텍스트 방향 미검증** — 회전 성분만 반영하고
  미러는 무시하도록 구현했으나, 샘플에 해당 사례가 없어 실제 렌더로 확인하지 못했다.
- **텍스트 크기 계수 0.6은 경험값** — PDF 실측으로 얻은 원본 cap height 비율(약 8.2 EDIF
  단위)에 맞춰 재조정할 여지가 있으나 이번 단계에서는 손대지 않았다.
- **`net_names=keep` 모드의 자동 넷 라벨 배치** — 와이어 끝점(부품 핀 근처)에 라벨이
  놓여 부품과 겹쳐 보일 수 있다(시각적 문제, 연결에는 무영향). 라벨 위치 개선은 다음
  단계 과제.
- **인스턴스 단위 `INVISIBLEPIN` 오버라이드 미반영** — 셀(라이브러리) 단위 숨김 값만
  반영하고, 인스턴스별 예외는 읽지 않는다.
- **GUI 결과 보관은 참조 방식** — 마지막 `PipelineResult`를 워커 스레드가 큐로 넘긴 뒤
  Tk 스레드가 참조로 들고 있는다. (**락은 쓰지 않는다** — 이전 판의 "락으로 직렬화"라는
  설명은 사실과 달랐다. 결과 객체는 오직 Tk 스레드에서만 읽고 쓰며, 워커 스레드는
  `queue.Queue`에 넣기만 하고 `after(100,...)` 폴링이 꺼내 반영한다. 실행 중 재실행은
  `running` 플래그로 막힌다.) 남는 제한은 수명뿐이다 — 대형 설계를 연속으로 여러 번
  변환하면 이전 결과 참조가 곧바로 해제되지 않아 메모리 사용량이 잠시 누적될 수 있다.
- **MCP `convert`는 동시에 하나만 실행 가능**(동기 실행) — 여러 변환을 동시에 요청하면
  뒤의 요청은 앞이 끝날 때까지 대기한다.
- **자리표시 페이지(`99-PCB-ONLY`)는 고정 A4 격자 배치** — 보드 전용 부품이 아주 많으면
  한 페이지 안에서 겹치거나 잘릴 수 있다(레이아웃 자동 조정 없음).
- ~~`add_board_only_parts`에 이미 회로도에 있는 레퍼런스를 넣으면 중복 추가를 막지 않는다~~
  → **2026-09-09 정정·수정 완료.** 원래부터 중복 배치는 하지 않았다(그런 레퍼런스는 건너뛰고
  `placeholder part <REF>: already in the schematic; skipped` 이슈만 남긴다). 다만 건너뛴
  레퍼런스까지 [3]/[4] 기준 넷리스트를 보강해 검증이 잘못 FAIL 할 수 있던 문제가 있었고,
  지금은 걸러 낸다. 이미 회로도에 있는 레퍼런스를 `--add-board-part`로 넣어도 안전하다
  (이슈 목록에 위 메시지만 남는다).
- ~~`agents.py`의 `augment_reference` import 중복~~ → **파일을 잘못 적은 기술이었다.**
  중복은 `pipeline.py`에 있었고 2026-09-09 에 한 곳으로 합쳤다.
- **`run_agents`의 핀 타입 제안은 기본 미선택** — 자동 일괄 적용 스크립트를 짤 때
  `selected=True`로 직접 켜지 않으면 아무 것도 반영되지 않는다는 점에 유의.
- **`ApiBackend`(Anthropic API) 라이브 경로 미검증** — 이 PC에 API 키가 없어 실제 HTTP
  왕복은 확인하지 못했다(단위 테스트는 `FakeBackend`로 커버). API 키가 있는 환경에서
  최초 1회 확인 권장.
- **exe(특히 GUI) 창 렌더링은 헤드리스 환경에서 미검증** — 패키징 자체(빌드 성공, 파일
  크기, `--selftest` 동작)는 확인했지만, 실제 디스플레이가 있는 PC에서 창이 정상
  렌더링되는지는 별도로 사람이 한 번 띄워 확인할 것.
- **`sanitize_fp_name` 이름 충돌 가능성**(3단계-A에서 이월) — 서로 다른 풋프린트 ID가
  금지 문자 치환 후 같은 파일명이 되면 나중 것이 조용히 덮어쓴다. 이번 샘플(35개)에는
  재현되지 않음.
- **다른 OrCAD 프로젝트로의 회귀 미확대** — 지금까지 모든 검증은 예시 보드 하나 기준이다.
  다른 설계에서는 위 항목들이 실제로 나타날 수 있으니 처음 쓸 때는 반드시 10장 절차대로
  KiCad에서 육안 확인을 거칠 것.

## 13. 부록

### 13.1 출력 폴더 구조 (`-o out/kicad` 예시, `--board`+`--pdf` 모두 지정한 경우)

```
out/kicad/
├── MYBOARD.kicad_pro                      # KiCad 프로젝트 파일 (더블클릭으로 열기)
├── MYBOARD.kicad_sch                      # 루트 회로도(하위 시트 심볼 포함)
├── MYBOARD.kicad_prl                      # 프로젝트 로컬 설정(kicad-cli가 생성)
├── 00-MCU.kicad_sch                       # 하위 시트(페이지)들 — 설계의 페이지 이름 그대로
├── 10-LIMIT SENSORS.kicad_sch
├── ... (설계 페이지 수만큼)
├── 99-PCB-ONLY.kicad_sch                  # 보드 전용 부품을 추가했을 때만 생김(5.3절)
├── orcad.kicad_sym                        # 변환된 심볼 라이브러리
├── sym-lib-table                          # 위 라이브러리를 프로젝트에 등록하는 테이블
├── MYBOARD.kicad_pcb                      # --board를 줬을 때만 생김(보드 임포트 결과)
├── PADS.pretty/                           # --board를 줬을 때만 생김(보드에서 추출한 풋프린트들, .kicad_mod)
├── fp-lib-table                           # 위 풋프린트 라이브러리를 프로젝트에 등록
├── pads_import/                           # --board가 .asc일 때 kicad-cli 임포트 중간 산출물
├── erc.json                               # kicad-cli ERC 결과(위반 목록, 종류별)
├── kicad_netlist.txt                      # kicad-cli가 뽑은 넷리스트(3차 검증 입력)
└── MYBOARD.pdf                            # --pdf를 줬을 때만 생김(회로도 PDF)
```

`out/`(저장소 루트 기준)는 gitignore 대상이라 커밋되지 않는다 — 다른 PC에서 처음 결과를
보려면 6.2절 명령으로 다시 생성해야 한다.

### 13.2 출력 폴더 구조 (`--dsn`/`--kicad-project` 경로, `--board`+`--pdf` 모두 지정한 경우)

`.DSN`/KiCad 프로젝트 입력은 EDIF 경로와 파일 종류가 대부분 같지만, 심볼 라이브러리가
회로도에 내장돼 있던 것을 뽑아 만든 것이고(`orcad_import.kicad_sym`), 하위 시트 이름이
`P01_`/`P02_` 접두를 쓰며, `.DSN` 임포트 로그가 추가로 남는다:

```
out/dsn/
├── MYBOARD.kicad_pro                      # KiCad 프로젝트 파일 (더블클릭으로 열기)
├── MYBOARD.kicad_sch                      # 루트 회로도 (0장 "정식 KiCad 10 포맷으로 재구성"의 결과, 하위 시트 심볼 포함)
├── P01_<첫 페이지 이름>.kicad_sch          # 나이틀리 임포터의 첫 시트를 재구성하며 이름을 바꾼 것
├── P02_<페이지 이름>.kicad_sch             # 이후 페이지들(재구성 시 붙는 순번 접두)
├── ... (설계 페이지 수만큼)
├── orcad_import.kicad_sym                 # 회로도에 내장돼 있던 심볼 정의를 추출한 라이브러리
├── sym-lib-table                          # 위 라이브러리를 프로젝트에 등록하는 테이블
├── MYBOARD.kicad_pcb                      # --board를 줬을 때만 생김(보드 임포트 결과, 정식 kicad-cli로 임포트)
├── PADS.pretty/                           # --board를 줬을 때만 생김(보드에서 추출한 풋프린트들, .kicad_mod)
├── fp-lib-table                           # 위 풋프린트 라이브러리를 프로젝트에 등록
├── pads_import/                           # --board가 .asc일 때 kicad-cli 임포트 중간 산출물
├── erc.json                               # kicad-cli ERC 결과(위반 목록, 종류별)
├── kicad_netlist.txt                      # kicad-cli가 뽑은 넷리스트(--netlist를 줬으면 [3] 입력, 아니면 [4]의 기준)
├── dsn_import.log                         # kicad-cli import 의 원본 출력(--dsn 입력일 때만 생김, 로캘에 따라 비ASCII 포함 가능)
└── MYBOARD.pdf                            # --pdf를 줬을 때만 생김(회로도 PDF)
```

`--kicad-project` 입력(이미 임포트해 둔 프로젝트를 그대로 씀)은 `dsn_import.log`가 없다는
점만 다르다. `--nightly-format`을 준 경우에는 재구성을 건너뛰므로 하위 시트 이름이
`P01_`/`P02_` 접두가 아니라 나이틀리 임포터가 원래 붙인 이름 그대로 남는다.

### 13.3 용어집

| 용어 | 뜻 |
|---|---|
| EDIF | Electronic Design Interchange Format. OrCAD Capture가 회로도를 텍스트로 내보내는 표준 포맷(이 도구는 2.0.0 버전만 다룸). |
| REF.PIN | "레퍼런스.핀번호" 형식(예: `R1.2`). 넷 비교의 최소 단위. |
| 넷(net) | 전기적으로 같은 전위인 핀들의 집합. |
| 1/2/3/4차 검증 | 7장 표 참고. |
| ERC | Electrical Rules Checker. KiCad가 회로도의 전기적 규칙 위반(핀 미접속, 전원 미구동 등)을 검사하는 기능. |
| DRC | Design Rules Checker. KiCad가 PCB의 물리적 규칙 위반(간격, 미접속 등)을 검사하는 기능. |
| 카퍼 포어(copper pour) | PCB의 넓은 구리 영역(주로 GND/전원 플레인). 폴리곤으로 정의되며, 익스포트에서 빠지면 그 영역으로 접속되는 패드가 전부 미접속으로 보인다(4.4절, 12장). |
| 풋프린트(footprint) / 데칼(decal) | 부품의 물리적 land pattern. KiCad는 "풋프린트", PADS는 "데칼"이라 부른다 — 이 도구에서는 같은 개념. |
| `Resolutions` | 보드/회로도 불일치에 대한 사용자 결정을 담는 내부 자료구조(5.3절 표의 4개 필드 + 핀 타입 오버라이드). |
| `PipelineOptions` / `PipelineResult` | `pipeline.run_pipeline()`의 입력/출력 타입. CLI 옵션, GUI 위젯 값, MCP 툴 인자가 전부 이 두 타입으로 변환·역변환된다. |
| Suggestion | AI 에이전트가 내는 제안 하나(적용 여부는 `selected` 필드로 사람이 결정). |
| 백엔드(backend) | 에이전트가 실제 LLM 호출을 위임하는 대상(`none`/`api`/`claude-cli`/`codex-cli`, 8장). |
| MCP | Model Context Protocol. 외부 AI 도구가 이 프로그램의 기능을 "툴"로 호출할 수 있게 하는 표준 프로토콜(9장). |
